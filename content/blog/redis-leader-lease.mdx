Ticker's ingestion pipeline reads a single upstream market feed and fans it out to every
consumer downstream. That's fine with one process running it. The moment there's more than one
— for redundancy, for horizontal scale, for a rolling deploy briefly running two — you have a
problem: the upstream feed doesn't want two readers. A duplicated read means duplicated ticks,
and duplicated ticks turn into wrong candles if nothing downstream is built to tolerate it.

## The options

Coordinating "exactly one of N processes is active" is a well-trodden problem, and the well-known
answer is a consensus system — etcd, ZooKeeper, a Raft group of your own. Each of those is also a
new distributed system to operate, with its own failure modes, for a project that already runs
Redis for the ingestion stream itself.

Redis already being in the stack changed the calculus. A `SET key value NX PX ttl` is atomic,
already available, and does exactly what's needed here: exactly one process can hold the key at a
time, and if that process dies without releasing it, the TTL expires the lock on its own.

## What the lock actually protects

```go
acquired, err := redis.SetNX(ctx, leaderKey, instanceID, leaseTTL)
if !acquired {
    return // another instance holds the lease — stand by, don't ingest
}
```

The holder renews the lease on an interval well inside the TTL, so a live process never loses its
lock to a slow tick or a GC pause — only an actually-dead process lets the lease expire. On clean
shutdown, the process releases the lock explicitly rather than waiting out the TTL, so a
deliberate restart doesn't leave downstream consumers waiting on a lease that nobody's coming back
for.

## The honest caveat

A Redis lease is not linearizable consensus. Under a real network partition, there's a window
where a lease could theoretically be held by a process Redis itself can no longer see cleanly. At
v1's actual scale — one ingestion instance — this entire mechanism is non-load-bearing; there's
never a second process to conflict with. It's built anyway, shaped for the day a second instance
exists, rather than retrofitted under pressure once it's actually needed.

## Would I use this at real scale?

For the specific failure mode — "don't let two processes both think they're the sole reader of an
external feed" — yes, with eyes open about what it isn't. It's not a replacement for a
consensus system in a context where split-brain is genuinely dangerous. It's a lightweight, honest
tool for a narrower job: cheap coordination when the cost of getting it briefly wrong (a few
duplicated ticks, deduplicated idempotently downstream anyway) is low.
